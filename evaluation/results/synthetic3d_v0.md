# Synthetic 3-D renders v0 — NHPT and Waiter – cup

**Synthetic 3-D renders, not real-camera evidence.** Physically based Blender (Eevee) renders of a laptop-camera view: 32 mm pegs standing in a perforated board on the printed sheet, a tapered cup with a blue tape ring and a handle, a skin-toned hand and forearm proxy built from primitives, shading, shadows, specular highlights, motion blur, sensor noise and JPEG q70. They exercise parallax, occlusion and lighting that the flat 2-D renders cannot; they are not people, real pegs or a real webcam, and the hand proxy is not a real hand (see *Limits*).

Regenerate: `cd services/session && uv run python ../../evaluation/blender/make_dataset_3d.py && uv run python ../../evaluation/scripts/eval_3d.py` (or `eval_3d.py --use-cache` to rescore the committed events).

OpenCV 5.0.0 · generated 2026-10-12 · pipeline at product defaults (debounce 2, clear 3), hand model on · matching ±1.0 s plus 1.0 s after the labelled time (eval.py) · 16 clips, 9167 frames.

## Limits

- Renders, not recordings: no real webcam auto-exposure, rolling shutter, lens distortion, real skin, real plastic or real paper.
- The hand is a proxy built from primitives (palm box, capsule fingers): the OpenCV Zoo hand model rarely detects it (see the hand-model coverage above), so pinch grasps, hand-near-hole verification and the cup's hand-based placement are under-exercised and the verified/unverified split mostly reflects the proxy, not the product. Real hands are expected to be detected far more often; that is unmeasured until real recordings exist.
- Labels come from the animation script (the instant the peg reaches the bottom of its hole, the cup touches down), not a human labeller; the product times events when it can see them, so a constant lag is expected.
- One motion script per exercise, varied by seed and speed; no tremor, hesitation, drops or wrong holes.
